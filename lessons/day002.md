### Regiones y Zonas: ¿Dónde Están Mis Datos?

Este es uno de los conceptos MÁS importantes de GCP. No es solo geografía, es **latencia, costos, compliance y disponibilidad**.

#### Regions: Áreas Geográficas

Una **region** es un área geográfica específica donde GCP tiene data centers.

**Ejemplos de regions:**
- `us-central1` - Iowa, USA
- `us-east1` - South Carolina, USA
- `europe-west1` - Bélgica
- `europe-west3` - Frankfurt, Alemania
- `asia-east1` - Taiwán
- `southamerica-east1` - São Paulo, Brasil

**Analogía:** Una region es como elegir en qué **ciudad** vas a almacenar tus cosas. Si vives en Madrid, no tiene sentido guardar todo en Tokio (sería lento y caro).

#### Zones: Data Centers Específicos

Cada region tiene **múltiples zones** (data centers físicos separados).

**Ejemplo:**
```
Region: us-central1 (Iowa)
├── Zone: us-central1-a (Data center A)
├── Zone: us-central1-b (Data center B)
├── Zone: us-central1-c (Data center C)
└── Zone: us-central1-f (Data center F)
```

**Analogía:** Si la region es Madrid, las zones son **almacenes específicos** en diferentes partes de la ciudad (norte, sur, centro).

#### ¿Por Qué Importan las Regiones y Zonas?

**1. Latencia (Velocidad)**
- **Problema:** Si tu servidor está en USA y tus usuarios en España, cada petición tarda ~100ms en cruzar el océano
- **Solución:** Usa una region europea (`europe-west1`) para usuarios en España
- **Regla:** Elige la region más cercana a tus usuarios

**2. Costos**
- **Problema:** No todas las regions cuestan lo mismo
- **Ejemplo:** `us-central1` (Iowa) es ~10% más barata que `us-east1` (South Carolina)
- **Solución:** Si la latencia no es crítica, usa regions más baratas
- **Regla:** Regions en USA suelen ser más baratas que en Europa/Asia

**3. Compliance (Leyes)**
- **Problema:** GDPR (Europa) requiere que datos de ciudadanos europeos se queden en Europa
- **Solución:** Usa solo regions europeas para datos de usuarios europeos
- **Regla:** Conoce las leyes de los países donde operas

**4. Disponibilidad de Servicios**
- **Problema:** No todos los servicios están en todas las regions
- **Ejemplo:** Algunas regions no tienen GPUs o servicios de ML
- **Solución:** Verifica que el servicio que necesitas esté disponible en tu region
- **Regla:** Regions principales (us-central1, europe-west1) tienen más servicios

**5. Alta Disponibilidad**
- **Problema:** Si un data center (zone) se cae, tu servicio se cae
- **Solución:** Distribuye tus recursos en múltiples zones de la misma region
- **Regla:** Para producción, usa al menos 2 zones diferentes

#### Cómo Elegir la Region Correcta

**Paso 1: ¿Dónde están tus usuarios?**
- España/Portugal → `europe-southwest1` (Madrid) o `europe-west1` (Bélgica)
- Latinoamérica → `southamerica-east1` (São Paulo) o `us-east1` (más barato)
- Global → Múltiples regions con load balancer

**Paso 2: ¿Qué leyes aplican?**
- GDPR (Europa) → Solo regions europeas
- Datos sensibles → Regions en el país de origen

**Paso 3: ¿El presupuesto es crítico?**
- Sí → Usa `us-central1` (Iowa) o `us-east1` (South Carolina)
- No → Prioriza latencia y compliance

**Paso 4: ¿Qué servicios necesitas?**
- Verifica disponibilidad en: https://cloud.google.com/about/locations

### APIs: Los Servicios de GCP

En GCP, cada servicio es una **API** que debes **habilitar** antes de usarla.

**Analogía:** Habilitar una API es como **instalar una app** en tu teléfono. Tu teléfono (proyecto) tiene capacidad para muchas apps (APIs), pero solo instalas las que necesitas.

#### ¿Por Qué No Están Todas Habilitadas por Defecto?

1. **Seguridad:** Menos APIs habilitadas = menor superficie de ataque
2. **Costos:** Algunas APIs tienen costos aunque no las uses
3. **Organización:** Solo habilitas lo que realmente necesitas
4. **Performance:** Menos servicios = consola más rápida

#### Cómo Habilitar una API

**Método 1: Desde la Búsqueda (Más Rápido)**
1. Haz clic en 🔍 (barra de búsqueda)
2. Escribe el nombre del servicio (ej: "Cloud Storage")
3. Haz clic en el servicio en los resultados
4. Si no está habilitado, verás un botón azul **"ENABLE"** o **"HABILITAR"**
5. Haz clic y espera unos segundos

**Método 2: Desde APIs & Services**
1. Menú hamburguesa (☰) → **APIs & Services** → **Library**
2. Verás todas las APIs disponibles (miles)
3. Usa la búsqueda para encontrar la que necesitas
4. Haz clic en la API
5. Haz clic en **"ENABLE"**

**Método 3: Desde la Línea de Comandos (gcloud)**
```bash
# Habilitar Cloud Storage
gcloud services enable storage.googleapis.com

# Habilitar Compute Engine
gcloud services enable compute.googleapis.com

# Ver APIs habilitadas
gcloud services list --enabled
```

#### APIs Comunes que Vas a Usar

| Servicio | API Name | Para Qué Sirve |
|----------|----------|----------------|
| Cloud Storage | `storage.googleapis.com` | Guardar archivos |
| Compute Engine | `compute.googleapis.com` | Crear máquinas virtuales |
| BigQuery | `bigquery.googleapis.com` | Análisis de datos |
| Cloud SQL | `sqladmin.googleapis.com` | Bases de datos SQL |
| Pub/Sub | `pubsub.googleapis.com` | Mensajería entre servicios |
| Cloud Functions | `cloudfunctions.googleapis.com` | Funciones serverless |

#### Gestionar APIs Habilitadas

**Ver APIs habilitadas:**
1. Menú hamburguesa → **APIs & Services** → **Library**
2. Haz clic en la pestaña **"ENABLED"** (arriba)
3. Verás la lista de APIs activas en tu proyecto

**Deshabilitar una API:**
1. Ve a la API en la Library
2. Haz clic en **"MANAGE"** (Gestionar)
3. Haz clic en **"DISABLE"** (arriba)
4. **Cuidado:** Esto puede romper recursos que dependan de esa API

### Billing: Entender la Factura de GCP

El billing es CRÍTICO. Un Cloud Architect que no entiende costos no es profesional.

#### Estructura del Billing en GCP

```
Billing Account (Cuenta de facturación)
├── Project 1 (gcp-course-dev)
│   ├── Cloud Storage: $0.50
│   ├── Compute Engine: $2.30
│   └── BigQuery: $1.20
├── Project 2 (gcp-course-staging)
│   └── ...
└── Project 3 (gcp-course-prod)
    └── ...
```

**Analogía:** Es como tu factura de servicios públicos:
- **Billing Account:** Es tu cuenta principal (como tu cuenta bancaria)
- **Projects:** Son como diferentes medidores (luz, agua, gas)
- **Resources:** Son los electrodomésticos que consumen

#### Cómo Ver tu Billing

**1. Dashboard de Billing:**
1. Menú hamburguesa (☰) → **Billing**
2. Verás:
   - **Crédito disponible:** Tu saldo del free tier ($300)
   - **Uso actual:** Cuánto has gastado este mes
   - **Gráfico de costos:** Desglose por servicio

**2. Desglose por Proyecto:**
1. En Billing, haz clic en **"Go to billing account"**
2. Verás todos tus proyectos y cuánto gasta cada uno
3. Haz clic en un proyecto para ver el detalle

**3. Desglose por Servicio:**
1. Dentro de un proyecto, ve a la pestaña **"Cost breakdown"**
2. Verás cuánto gasta cada servicio (Storage, Compute, etc.)
3. Puedes filtrar por fecha, servicio, SKU

#### Conceptos Clave de Billing

**1. Free Tier (Nivel Gratuito)**
- GCP te da **$300 USD** de crédito por 90 días
- Algunos servicios tienen **free tier permanente** (siempre gratis hasta cierto límite)
- Ejemplo: Cloud Functions - 2M invocaciones/mes gratis

**2. Pay-as-you-go (Paga por lo que usas)**
- Solo pagas por lo que consumes
- Se cobra por segundo (no por hora completa)
- Ejemplo: Si usas una VM por 30 minutos, pagas 30 minutos

**3. Sustained Use Discounts (Descuentos por Uso Sostenido)**
- Automáticos por usar recursos todo el mes
- Hasta 30% de descuento
- No requiere compromiso

**4. Committed Use Discounts (Descuentos por Compromiso)**
- Compromiso de 1 o 3 años
- Hasta 57% de descuento
- Para workloads predecibles

#### Cómo Controlar Costos desde el Día 1

**1. Configura Budgets y Alerts (OBLIGATORIO)**
1. Billing → **Budgets & alerts**
2. Crea un budget (ej: $50/mes)
3. Configura alertas al 50%, 80%, 100%
4. Recibirás emails cuando te acerques al límite

**2. Revisa el Billing Diariamente (al inicio)**
- Dedica 5 minutos cada mañana a ver tu billing
- Identifica picos de uso inesperados
- Apaga recursos que no uses

**3. Usa la Calculadora de Precios**
- https://cloud.google.com/products/calculator
- Estima costos ANTES de crear recursos grandes
- Compara regions y configuraciones

**4. Apaga Recursos que No Usas**
- VMs: Detenlas cuando no las uses (ahorras ~70%)
- Clusters: Elimínalos después de experimentar
- Snapshots: Borra los antiguos

**5. Usa Labels para Tracking**
- Etiqueta recursos con `environment`, `team`, `project`
- Permite hacer chargeback (saber quién gasta qué)
- Lo veremos en detalle más adelante

#### Errores Comunes de Billing

**Error 1: No configurar alerts**
- **Consecuencia:** Te quedas sin crédito sin darte cuenta
- **Solución:** Configura budgets ANTES de crear recursos

**Error 2: Dejar VMs corriendo 24/7**
- **Consecuencia:** Una VM pequeña puede costar $20-50/mes
- **Solución:** Apaga VMs de desarrollo cuando no las uses

**Error 3: No entender los costos de red**
- **Consecuencia:** Transferir datos entre regions cuesta dinero
- **Solución:** Mantén datos y compute en la misma region

**Error 4: Crear recursos en regions caras**
- **Consecuencia:** Mismos recursos, 20-30% más caro
- **Solución:** Usa regions baratas para desarrollo (us-central1)

## Mentalidad de Cloud Architect

Un Cloud Architect piensa así sobre regiones y billing:

1. **"¿Dónde deben estar mis datos?"**
   - Cerca de los usuarios (latencia)
   - En el país correcto (compliance)
   - En la region más barata que cumpla los requisitos

2. **"¿Cuánto va a costar esto a escala?"**
   - Calcula costos unitarios (por usuario, por transacción)
   - Proyecta a 10x y 100x el uso actual
   - Identifica oportunidades de optimización

3. **"¿Cómo voy a trackear costos?"**
   - Labels desde el día 1
   - Budgets por proyecto/equipo
   - Reportes semanales de spending

4. **"¿Qué pasa si me paso del presupuesto?"**
   - Alerts configuradas
   - Plan de acción (apagar recursos no críticos)
   - Comunicación con stakeholders

5. **"¿Estoy usando la region correcta?"**
   - Revisa latencia desde diferentes ubicaciones
   - Verifica compliance con leyes locales
   - Considera disaster recovery (multi-region)

## Errores Comunes en Producción

### 1. Elegir la Region Incorrecta
**Error:** Crear todo en `us-central1` cuando tus usuarios están en Europa
**Consecuencia:** Latencia alta (~100ms extra), mala experiencia de usuario
**Solución:** Usa regions cercanas a tus usuarios

### 2. No Habilitar APIs Necesarias
**Error:** Intentar usar un servicio sin habilitar la API
**Consecuencia:** Errores confusos, pérdida de tiempo
**Solución:** Habilita APIs antes de usarlas, verifica en Library

### 3. Ignorar el Billing hasta que es Tarde
**Error:** No revisar billing hasta fin de mes
**Consecuencia:** Sorpresas en la factura, presupuesto excedido
**Solución:** Revisa billing diariamente, configura alerts

### 4. Dejar Recursos de Prueba Encendidos
**Error:** Crear VMs/clusters para probar y olvidar apagarlos
**Consecuencia:** Costos innecesarios acumulándose
**Solución:** Programa recordatorios, usa auto-shutdown

### 5. No Entender los Costos de Red
**Error:** Mover datos entre regions sin considerar costos
**Consecuencia:** Egress costs (salida de datos) pueden ser significativos
**Solución:** Mantén datos y compute en la misma region cuando sea posible

## Examen Tip

**Pregunta tipo certificación:**

Una empresa con usuarios en España y México necesita desplegar una aplicación web. ¿Qué factor es MÁS importante al elegir la region de GCP?

A) Elegir la region más barata (us-central1)
B) Elegir una region cercana a los usuarios para reducir latencia
C) Elegir la region con más zonas disponibles
D) Elegir la region donde GCP tiene su headquarters

**Respuesta correcta:** B

**Explicación:** La latencia es crítica para la experiencia de usuario. Una region cercana (ej: europe-southwest1 para España, southamerica-east1 para México) reduce la latencia significativamente. El costo es importante pero secundario a la experiencia de usuario. El número de zonas y la ubicación del headquarters de Google son irrelevantes para esta decisión.

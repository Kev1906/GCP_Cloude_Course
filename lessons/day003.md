# Day 003: Organization, Folders, Projects - La Jerarquía de Recursos

Al final del día sabrás cómo se organiza una empresa real en GCP y por qué cada nivel existe.

## Conceptos Clave

### La Jerarquía de Recursos de GCP

GCP organiza todo en una jerarquía de 4 niveles. Esta es la estructura MÁS importante que debes entender.

```
Organization Node (Nivel raíz - tu empresa completa)
├── Folder (Departamento o división)
│   ├── Folder (Sub-departamento)
│   │   ├── Project (Aplicación específica)
│   │   │   ├── Compute Engine (VM)
│   │   │   ├── Cloud Storage (Bucket)
│   │   │   └── BigQuery (Dataset)
│   │   └── Project (Otra aplicación)
│   └── Project (Proyecto directo del folder)
├── Folder (Otro departamento)
│   └── Project
└── Project (Proyecto sin folder - no recomendado en producción)
```

**Analogía con una empresa real:**

```
Empresa (Organization)
├── División Tecnología (Folder)
│   ├── Departamento Ingeniería (Folder)
│   │   ├── Proyecto E-commerce (Project)
│   │   │   ├── Servidores (Resources)
│   │   │   ├── Base de datos (Resources)
│   │   │   └── Almacenamiento (Resources)
│   │   └── Proyecto App Móvil (Project)
│   └── Departamento Datos (Folder)
│       └── Proyecto Analytics (Project)
├── División Finanzas (Folder)
│   └── Departamento Contabilidad (Folder)
│       └── Proyecto ERP (Project)
└── Proyecto Especial Temporal (Project - sin folder)
```

**Analogía con tu computadora:**

```
Disco C:\ (Organization)
├── Carpeta Usuarios (Folder)
│   ├── Carpeta Juan (Folder)
│   │   ├── Proyecto Tesis (Project)
│   │   │   ├── documento.docx (Resource)
│   │   │   ├── datos.csv (Resource)
│   │   │   └── script.py (Resource)
│   │   └── Proyecto Curso (Project)
│   └── Carpeta María (Folder)
│       └── Proyecto Trabajo (Project)
├── Carpeta Programas (Folder)
│   └── Carpeta Office (Project)
└── archivo_temporal.txt (Resource suelto - no recomendado)
```

### Organization Node: La Raíz de Todo

El **Organization Node** representa a tu empresa completa en GCP. Es el nivel más alto de la jerarquía.

**¿Qué es?**
- Es el "paraguas" que cubre todos tus recursos de GCP
- Representa legalmente a tu organización (empresa, institución)
- Se crea automáticamente cuando te registras en G Suite o Cloud Identity
- Si usas una cuenta personal de Gmail, NO tienes Organization Node (solo tienes proyectos sueltos)

**¿Para qué sirve?**
- **Políticas globales:** Reglas que aplican a TODA tu empresa
- **Seguridad centralizada:** Controles que heredan todos los proyectos
- **Billing unificado:** Una sola cuenta de facturación para todo
- **Gestión de identidades:** Control de acceso desde un solo lugar

**Analogía:** El Organization Node es como la **Constitución** de tu empresa. Define las reglas fundamentales que todos deben seguir.

**Ejemplo de políticas en el Organization Node:**
- "Ningún proyecto puede usar regions fuera de Europa" (compliance GDPR)
- "Todos los buckets deben tener encriptación habilitada" (seguridad)
- "Solo los admins pueden crear proyectos nuevos" (gobernanza)

**¿Cómo saber si tienes Organization Node?**
1. Ve a la consola de GCP
2. Menú hamburguesa (☰) → **IAM & Admin** → **Settings** (Configuración)
3. Si ves un "Organization ID", tienes Organization Node
4. Si no ves nada, estás usando una cuenta personal sin Organization

**Nota para el curso:** Si estás usando una cuenta personal de Gmail, probablemente no tengas Organization Node. No te preocupes, puedes simular la estructura con Folders y Projects. Más adelante veremos cómo crear un Organization Node con Cloud Identity (gratis).

### Folders: Organizando por Lógica de Negocio

Los **Folders** son contenedores lógicos para organizar proyectos. No tienen recursos propios, solo agrupan proyectos.

**¿Para qué sirven?**
- **Organización:** Agrupar proyectos por equipo, departamento, ambiente
- **Herencia de políticas:** Las políticas del folder se aplican a todos sus proyectos
- **Herencia de permisos:** Los permisos del folder se aplican a todos sus proyectos
- **Control de costos:** Puedes ver costos agregados por folder

**Reglas importantes:**
1. Los folders pueden contener otros folders (hasta 7 niveles de profundidad)
2. Los folders pueden contener proyectos
3. Los folders NO pueden contener recursos directamente (VMs, buckets, etc.)
4. Los proyectos pueden moverse entre folders
5. Los folders pueden tener políticas y permisos propios

**Analogía:** Los folders son como **carpetas en un archivador**. No contienen los documentos directamente, sino otras carpetas más pequeñas que sí contienen los documentos.

**Ejemplos de estructura de folders:**

**Estructura por ambiente:**
```
Organization
├── Folder: Development
│   ├── Project: ecommerce-dev
│   ├── Project: analytics-dev
│   └── Project: mobile-dev
├── Folder: Staging
│   ├── Project: ecommerce-staging
│   ├── Project: analytics-staging
│   └── Project: mobile-staging
└── Folder: Production
    ├── Project: ecommerce-prod
    ├── Project: analytics-prod
    └── Project: mobile-prod
```

**Estructura por equipo:**
```
Organization
├── Folder: Team-Platform
│   ├── Project: infra-dev
│   ├── Project: infra-staging
│   └── Project: infra-prod
├── Folder: Team-Data
│   ├── Project: data-dev
│   ├── Project: data-staging
│   └── Project: data-prod
└── Folder: Team-Frontend
    ├── Project: web-dev
    ├── Project: web-staging
    └── Project: web-prod
```

**Estructura mixta (la más común en empresas reales):**
```
Organization
├── Folder: Common
│   ├── Project: shared-services (DNS, redes, monitoring)
│   └── Project: security-tools (logs, auditoría)
├── Folder: Environments
│   ├── Folder: Development
│   │   ├── Folder: Team-Data
│   │   │   ├── Project: data-pipeline-dev
│   │   │   └── Project: data-warehouse-dev
│   │   └── Folder: Team-Platform
│   │       └── Project: infra-dev
│   ├── Folder: Staging
│   │   └── ... (similar a Development)
│   └── Folder: Production
│       └── ... (similar a Development)
└── Folder: Sandbox
    └── Project: experiments (proyectos de prueba sin control estricto)
```

### Projects: La Unidad de Trabajo

Ya conoces los projects del Day 1, pero ahora los veremos en contexto de la jerarquía completa.

**Características clave:**
1. **Todo recurso pertenece a un project** - No hay excepciones
2. **Los projects tienen un ID único** - No se puede cambiar después de crear
3. **Los projects tienen un nombre** - Se puede cambiar, pero no es recomendable
4. **Los projects tienen un número** - Generado automáticamente, no se puede cambiar
5. **Los projects pueden moverse entre folders** - Pero cuidado con los permisos

**Analogía:** Un project es como un **contenedor de shipping**. Todo lo que va dentro (servidores, bases de datos, archivos) pertenece a ese contenedor. El contenedor tiene una etiqueta única (project ID) que lo identifica en todo el mundo.

**Diferencia entre Project Name, ID y Number:**

```
Project Name: gcp-course-dev
├── Se puede cambiar (pero no recomendado)
├── Es legible para humanos
└── No necesita ser único globalmente

Project ID: gcp-course-dev-123456
├── NO se puede cambiar después de crear
├── Debe ser único globalmente (en todo GCP)
├── Se usa en comandos, APIs, URLs
└── Formato: letras minúsculas, números, guiones

Project Number: 123456789012
├── Generado automáticamente por GCP
├── NO se puede cambiar
├── Se usa internamente por GCP
└── Formato: número de 12 dígitos
```

**¿Cuántos projects necesitas?**

**Regla profesional:** Un project por aplicación por ambiente.

**Ejemplo para DataMartX:**
```
ecommerce-dev          → Aplicación e-commerce en desarrollo
ecommerce-staging      → Aplicación e-commerce en staging
ecommerce-prod         → Aplicación e-commerce en producción
analytics-dev          → Pipeline de datos en desarrollo
analytics-staging      → Pipeline de datos en staging
analytics-prod         → Pipeline de datos en producción
shared-networking      → Redes compartidas (VPCs)
shared-monitoring      → Logging y monitoring centralizado
```

**Errores comunes:**
- ❌ Un solo project para todo (imposible de gestionar a escala)
- ❌ Un project por ambiente sin separar aplicaciones (difícil de entender costos)
- ✅ Un project por aplicación por ambiente (limpio, escalable)

### Cómo Fluyen los Permisos en la Jerarquía

Este es un concepto CRÍTICO. Los permisos en GCP se **heredan de arriba hacia abajo**.

```
Organization (Política: "Solo admins pueden crear projects")
├── Folder: Development
│   ├── Permiso: "Equipo dev puede crear recursos"
│   ├── Project: app-dev
│   │   ├── Hereda: "Solo admins pueden crear projects" (de Organization)
│   │   ├── Hereda: "Equipo dev puede crear recursos" (de Folder)
│   │   └── Permiso propio: "Juan puede administrar BigQuery"
│   └── Project: data-dev
│       └── Hereda lo mismo que app-dev
└── Folder: Production
    ├── Permiso: "Solo equipo senior puede crear recursos"
    └── Project: app-prod
        ├── Hereda: "Solo admins pueden crear projects" (de Organization)
        ├── Hereda: "Solo equipo senior puede crear recursos" (de Folder)
        └── NO hereda permisos de Development (son folders hermanos)
```

**Reglas de herencia:**
1. Los permisos se heredan de padre a hijo
2. Un hijo NO puede tener más permisos que su padre
3. Los permisos se acumulan (si tienes permiso en folder Y en project, tienes ambos)
4. Los permisos de folders hermanos NO se comparten
5. Puedes agregar permisos en cualquier nivel, pero no puedes quitar permisos heredados (solo denying explícitamente)

**Analogía:** Es como los permisos en una empresa:
- El CEO (Organization) dice: "Solo directores pueden aprobar gastos > $10,000"
- El Director de Tecnología (Folder) dice: "Solo líderes de equipo pueden aprobar gastos > $1,000"
- Un proyecto hereda ambas reglas: necesita aprobación del líder de equipo para > $1,000 y del director para > $10,000

### Cómo Fluyen los Costos en la Jerarquía

Los costos también se agregan jerárquicamente.

```
Organization: Costo total = $10,000/mes
├── Folder: Development: $2,000/mes (suma de sus projects)
│   ├── Project: app-dev: $800/mes
│   ├── Project: data-dev: $700/mes
│   └── Project: mobile-dev: $500/mes
├── Folder: Production: $7,000/mes
│   ├── Project: app-prod: $3,000/mes
│   ├── Project: data-prod: $2,500/mes
│   └── Project: mobile-prod: $1,500/mes
└── Folder: Sandbox: $1,000/mes
    └── Project: experiments: $1,000/mes
```

**¿Por qué importa esto?**
- Puedes hacer **chargeback** (cobrar a cada departamento su uso real)
- Puedes hacer **showback** (mostrar a cada equipo cuánto gasta)
- Puedes configurar **budgets por folder** (no solo por project)
- Puedes identificar qué área gasta más y optimizar

**Analogía:** Es como la factura de servicios de tu casa:
- Factura total: $200/mes
- Habitación Juan: $60 (30%)
- Habitación María: $80 (40%)
- Áreas comunes: $60 (30%)
- Cada persona paga según lo que usa

### Organization Policies: Control Centralizado

Las **Organization Policies** son reglas que se aplican en el Organization Node (o en folders) y se heredan a todos los projects.

**Ejemplos de políticas comunes:**

**1. Restringir regiones permitidas:**
```
Política: constraints/compute.vmExternalIpAccess
Valor: Deny en Production, Allow en Development
Efecto: En producción, las VMs no pueden tener IP pública
```

**2. Requerir encriptación:**
```
Política: constraints/storage.uniformBucketLevelAccess
Valor: Allow (requerido)
Efecto: Todos los buckets deben tener acceso uniforme (más seguro)
```

**3. Restringir servicios públicos:**
```
Política: constraints/serviceuser.services
Valor: Deny: compute.googleapis.com en Sandbox
Efecto: En Sandbox no se pueden crear VMs
```

**¿Por qué usar Organization Policies?**
- **Seguridad:** Reglas obligatorias para toda la empresa
- **Compliance:** Cumplir regulaciones (GDPR, HIPAA, PCI DSS)
- **Gobernanza:** Control centralizado sin configurar cada project
- **Consistencia:** Todos los projects siguen las mismas reglas

**Nota:** Las Organization Policies requieren un Organization Node. Si usas cuenta personal de Gmail, no puedes usarlas directamente, pero puedes simular el concepto con permisos IAM en folders.

## Mentalidad de Cloud Architect

Un Cloud Architect piensa así sobre la jerarquía de organización:

1. **"¿Cómo estructuro mi organización desde el día 1?"**
   - Diseña la estructura ANTES de crear proyectos
   - Piensa en el futuro (¿qué pasaría si crecemos 10x?)
   - La estructura debe reflejar cómo opera la empresa

2. **"¿Cómo heredan permisos mis proyectos?"**
   - Define permisos en el nivel más alto posible (principio de menor privilegio)
   - No des permisos en cada project individualmente
   - Usa folders para agrupar proyectos con los mismos permisos

3. **"¿Cómo voy a trackear costos?"**
   - La estructura de folders debe facilitar el chargeback
   - Cada equipo/departamento debe tener su propio folder
   - Configura budgets por folder, no solo por project

4. **"¿Qué políticas necesitan ser globales?"**
   - Seguridad: encriptación, acceso público, regiones permitidas
   - Compliance: retención de datos, auditoría, logging
   - Costos: límites de recursos, tipos de máquinas permitidas

5. **"¿Cómo manejo el crecimiento?"**
   - La estructura debe escalar sin reestructurar
   - Deja espacio para nuevos equipos y aplicaciones
   - Documenta la estructura para que todos la entiendan

## Errores Comunes en Producción

### 1. No Tener una Estructura de Organización
**Error:** Crear proyectos sin pensar en la estructura
**Consecuencia:** Cientos de proyectos sueltos, imposibles de gestionar
**Solución:** Diseña la estructura ANTES de crear el primer proyecto

### 2. Un Solo Proyecto para Todo
**Error:** Poner todos los recursos en un solo proyecto
**Consecuencia:** Permisos confusos, costos imposibles de trackear, riesgos de seguridad
**Solución:** Un proyecto por aplicación por ambiente

### 3. No Usar Folders
**Error:** Crear proyectos directamente en la raíz (Organization)
**Consecuencia:** No puedes aplicar políticas ni permisos de forma eficiente
**Solución:** Usa folders para agrupar proyectos lógicamente

### 4. Dar Permisos en Cada Proyecto
**Error:** Configurar IAM en cada proyecto individualmente
**Consecuencia:** Inconsistencias, errores, difícil de auditar
**Solución:** Da permisos en el nivel de folder cuando sea posible

### 5. Ignorar la Herencia de Permisos
**Error:** No entender que los permisos se heredan
**Consecuencia:** Usuarios con más permisos de los necesarios (riesgo de seguridad)
**Solución:** Revisa regularmente quién tiene acceso a qué nivel

### 6. No Planificar para Compliance
**Error:** No considerar regulaciones al diseñar la estructura
**Consecuencia:** Multas, auditorías fallidas, problemas legales
**Solución:** Diseña la estructura pensando en compliance desde el inicio

## Ejemplos Prácticos

### Ejemplo 1: Ver tu Organization Node

**Objetivo:** Verificar si tienes un Organization Node y entender tu estructura actual

1. **Ve a la consola de GCP:**
   - https://console.cloud.google.com/

2. **Navega a IAM & Admin:**
   - Menú hamburguesa (☰) → **IAM & Admin** → **Settings**
   - O busca "Settings" en la barra de búsqueda

3. **Observa la información:**
   - **Organization ID:** Si ves un número, tienes Organization Node
   - **Organization name:** El nombre de tu organización
   - **Project ID:** El ID del proyecto actual

4. **Si NO tienes Organization Node:**
   - Verás un mensaje: "This project is not associated with an organization"
   - Esto es normal si usas cuenta personal de Gmail
   - Puedes simular la estructura con folders y projects

5. **Si SÍ tienes Organization Node:**
   - Verás el Organization ID (ej: 123456789012)
   - Puedes crear folders y policies a nivel de organización

### Ejemplo 2: Crear Folders para DataMartX

**Objetivo:** Crear una estructura de folders profesional

1. **Ve a Resource Manager:**
   - Menú hamburguesa (☰) → **IAM & Admin** → **Manage Resources**
   - O busca "Manage resources" en la barra de búsqueda

2. **Verás tu proyecto actual:**
   - `gcp-course-dev` (o el nombre que le diste)

3. **Crea el primer folder:**
   - Haz clic en **"CREATE FOLDER"** (arriba)
   - **Name:** `DataMartX`
   - **Location:** Selecciona tu Organization (si tienes) o "No organization"
   - Haz clic en **"CREATE"**

4. **Crea folders de ambientes:**
   - Dentro del folder `DataMartX`, crea:
     - **Name:** `Development`
     - **Location:** `DataMartX` (el folder que acabas de crear)
   - Repite para:
     - **Name:** `Staging`
     - **Name:** `Production`
     - **Name:** `Sandbox`

5. **Crea folders de equipos dentro de Development:**
   - Selecciona el folder `Development`
   - Crea:
     - **Name:** `Team-Data`
     - **Name:** `Team-Platform`
     - **Name:** `Team-Frontend`

6. **Tu estructura debería verse así:**
   ```
   DataMartX (Folder)
   ├── Development (Folder)
   │   ├── Team-Data (Folder)
   │   ├── Team-Platform (Folder)
   │   └── Team-Frontend (Folder)
   ├── Staging (Folder)
   ├── Production (Folder)
   └── Sandbox (Folder)
   ```

7. **Verifica la estructura:**
   - Navega por los folders haciendo clic en ellos
   - Observa los breadcrumbs (migas de pan) arriba: `DataMartX > Development > Team-Data`
   - Practica moviéndote entre niveles

### Ejemplo 3: Crear Proyectos dentro de Folders

**Objetivo:** Crear proyectos organizados en la estructura de folders

1. **Selecciona el folder correcto:**
   - En Resource Manager, navega a: `DataMartX > Development > Team-Data`

2. **Crea un proyecto dentro del folder:**
   - Haz clic en **"CREATE PROJECT"**
   - **Project name:** `datamartx-data-dev`
   - **Organization:** Debería mostrar `DataMartX > Development > Team-Data`
   - **Location:** Debería estar dentro del folder `Team-Data`
   - Haz clic en **"CREATE"**

3. **Crea más proyectos:**
   - En `DataMartX > Development > Team-Platform`:
     - **Project name:** `datamartx-platform-dev`
   - En `DataMartX > Staging > Team-Data`:
     - **Project name:** `datamartx-data-staging`
   - En `DataMartX > Production > Team-Data`:
     - **Project name:** `datamartx-data-prod`

4. **Verifica la estructura completa:**
   - Ve a Resource Manager
   - Deberías ver:
   ```
   DataMartX
   ├── Development
   │   ├── Team-Data
   │   │   └── datamartx-data-dev (Project)
   │   └── Team-Platform
   │       └── datamartx-platform-dev (Project)
   ├── Staging
   │   └── Team-Data
   │       └── datamartx-data-staging (Project)
   └── Production
       └── Team-Data
           └── datamartx-data-prod (Project)
   ```

5. **Cambia entre proyectos:**
   - Usa el selector de proyecto (arriba) para cambiar
   - Observa cómo el contexto cambia
   - Cada proyecto está en su folder correspondiente

### Ejemplo 4: Mover Proyectos entre Folders

**Objetivo:** Aprender a reorganizar la estructura moviendo proyectos

1. **Selecciona un proyecto:**
   - En Resource Manager, encuentra `datamartx-data-dev`
   - Haz clic en los tres puntos (⋮) a la derecha del proyecto

2. **Mueve el proyecto:**
   - Haz clic en **"MOVE"**
   - Selecciona el nuevo destino: `DataMartX > Staging > Team-Data`
   - Haz clic en **"MOVE"**
   - **Advertencia:** Esto puede afectar permisos y políticas

3. **Verifica el movimiento:**
   - El proyecto ahora está en `Staging` en lugar de `Development`
   - Los permisos del folder `Staging` ahora aplican
   - Los permisos del folder `Development` ya no aplican

4. **Mueve el proyecto de vuelta:**
   - Repite el proceso para moverlo de vuelta a `Development > Team-Data`
   - Esto es útil si te equivocas en la estructura inicial

5. **Consideraciones al mover proyectos:**
   - **Permisos:** El proyecto hereda nuevos permisos del folder destino
   - **Políticas:** Las organization policies del nuevo folder aplican
   - **Billing:** El billing account puede cambiar (si los folders tienen diferentes billing)
   - **Servicios habilitados:** Se mantienen, pero verifica que sigan habilitados

### Ejemplo 5: Ver Costos por Folder

**Objetivo:** Entender cómo se agregan los costos en la jerarquía

1. **Ve a Billing:**
   - Menú hamburguesa (☰) → **Billing**

2. **Selecciona tu cuenta de billing:**
   - Haz clic en **"Go to billing account"**

3. **Explora el desglose por proyecto:**
   - Haz clic en **"Cost breakdown"**
   - En el filtro **"Project"**, verás todos tus proyectos
   - Observa cuánto gasta cada proyecto

4. **Agrupa por folder (si tienes Organization Node):**
   - En **"Group by"**, selecciona **"Folder"**
   - Verás los costos agregados por folder
   - Esto te dice cuánto gasta cada departamento/equipo

5. **Analiza los datos:**
   - ¿Qué folder gasta más?
   - ¿Qué proyecto dentro de cada folder es el más caro?
   - ¿Hay proyectos que no deberían estar en ese folder?

6. **Configura budgets por folder (si tienes Organization Node):**
   - Ve a **"Budgets & alerts"**
   - Crea un budget para el folder `Development`
   - Crea otro budget para el folder `Production`
   - Esto te permite controlar costos por departamento

## Comparación de Servicios

| Concepto | GCP | AWS | Azure |
|----------|-----|-----|-------|
| Nivel raíz | Organization Node | AWS Account (root) | Azure AD Tenant |
| Agrupación lógica | Folders | AWS Organizations OUs | Management Groups |
| Unidad de trabajo | Projects | AWS Accounts | Resource Groups |
| Políticas globales | Organization Policies | SCPs (Service Control Policies) | Azure Policies |
| Herencia de permisos | Sí (Organization → Folder → Project) | Sí (Root → OU → Account) | Sí (Tenant → Management Group → Resource Group) |
| Control de costos | Budgets por folder | AWS Budgets por OU | Azure Budgets por Management Group |

## Cost Considerations

**Costos de hoy:**
- **Organization Node:** GRATIS
- **Folders:** GRATIS (puedes crear hasta 200 folders por organización)
- **Projects:** GRATIS (puedes crear muchos projects)
- **Organization Policies:** GRATIS

**Costos potenciales si no organizas bien:**
- **Proyectos duplicados:** Dificulta trackear costos, lleva a gastos innecesarios
- **Permisos mal configurados:** Riesgo de seguridad, posibles multas de compliance
- **Sin budgets por folder:** No puedes hacer chargeback, costos fuera de control
- **Estructura plana:** Difícil de gestionar a escala, requiere más tiempo de administración

**Optimización desde el día 1:**
1. Diseña la estructura ANTES de crear proyectos
2. Usa folders para agrupar lógicamente
3. Configura budgets por folder
4. Documenta la estructura para tu equipo
5. Revisa la estructura mensualmente (¿sigue teniendo sentido?)

## Examen Tip

**Pregunta tipo certificación:**

Una empresa tiene múltiples departamentos (Ventas, Marketing, Ingeniería) y necesita aplicar diferentes políticas de seguridad a cada uno. ¿Cuál es la MEJOR forma de organizar los proyectos en GCP?

A) Crear un proyecto por departamento y aplicar políticas en cada proyecto
B) Crear un folder por departamento y aplicar políticas en cada folder
C) Crear todos los proyectos en la raíz de la Organization y aplicar políticas globales
D) Crear un solo proyecto y usar labels para separar departamentos

**Respuesta correcta:** B

**Explicación:** Los folders permiten aplicar políticas y permisos que se heredan a todos los proyectos dentro del folder. Esto es más eficiente que aplicar políticas en cada proyecto individualmente (opción A). La opción C no permite diferenciar políticas por departamento. La opción D usa labels, que son útiles para tracking de costos pero no para aplicar políticas de seguridad. Los folders son la herramienta correcta para organizar por lógica de negocio y aplicar políticas diferenciadas.

## Resumen

**Lo que aprendiste hoy:**

- **La jerarquía de GCP** tiene 4 niveles: Organization → Folders → Projects → Resources
- **Organization Node** representa a tu empresa completa y permite políticas globales
- **Folders** agrupan proyectos lógicamente y heredan políticas/permisos
- **Projects** son la unidad de trabajo donde creas todos los recursos
- **Los permisos se heredan** de arriba hacia abajo en la jerarquía
- **Los costos se agregan** jerárquicamente, permitiendo chargeback por departamento
- **Organization Policies** son reglas globales que aplican a toda la organización

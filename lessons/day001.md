# Day 001: GCP Architecture, Projects, Organizations, Folders

## Objetivo del Día

Comprender la jerarquía de recursos de GCP y cómo diseñar una estructura de organización escalable, segura y eficiente en costos. Aprenderás a pensar como un Cloud Architect al diseñar la fundación de una plataforma cloud empresarial.

## Contexto de Negocio

**Escenario:** DataMartX, marketplace internacional con operaciones en 15 países, está migrando su infraestructura on-premise a GCP. El CTO te pide diseñar la estructura de organización que soporte:
- 5 líneas de negocio (Marketplace, Logistics, Payments, Analytics, Corporate)
- 3 ambientes (Production, Staging, Development)
- 15 regiones geográficas
- Compliance con PCI DSS (pagos) y GDPR (Europa)
- Presupuesto anual de $2M en cloud

**Restricciones:**
- Separación clara entre ambientes
- Control de costos por línea de negocio
- Gobernanza centralizada con autonomía por equipo
- Auditoría completa de cambios

## Conceptos Clave

### Resource Hierarchy: Organization → Folders → Projects → Resources

La jerarquía de recursos de GCP es la columna vertebral de toda la plataforma. No es solo organización, es **gobernanza, seguridad y costos**.

```
Organization (datamartx.com)
├── Folder: Production
│   ├── Project: marketplace-prod
│   ├── Project: logistics-prod
│   └── Project: payments-prod
├── Folder: Staging
│   ├── Project: marketplace-staging
│   └── Project: analytics-staging
├── Folder: Development
│   └── Project: shared-dev
└── Folder: Shared Services
    ├── Project: networking
    └── Project: security
```

**Por qué importa:**
- **IAM policies** se heredan de arriba hacia abajo
- **Organization policies** aplican restricciones globales
- **Billing** se puede agrupar por folder
- **Quotas** se aplican a nivel de proyecto

### Organization: La Raíz de Todo

La Organization es el contenedor raíz que representa tu dominio de Google Workspace (o Cloud Identity). Solo hay UNA por empresa.

**Decisiones críticas:**
- **¿Quién es el Super Admin?** Debe ser un grupo, no un usuario individual
- **¿Múltiples organizaciones?** Solo si hay requisitos legales extremos (ej: fusión de empresas)
- **Organization policies:** Aplican a TODOS los proyectos. Úsalas para:
  - Restringir regiones permitidas
  - Forzar encryption con CMEK
  - Deshabilitar service accounts con claves
  - Controlar acceso a la red

**Error común:** Crear múltiples organizaciones por "comodidad". Esto multiplica la complejidad de gobernanza x10.

### Folders: Agrupación Lógica

Los folders organizan proyectos con propósitos específicos:

**Patrones comunes:**

1. **Por ambiente:**
```
Folder: Production
Folder: Staging  
Folder: Development
```

2. **Por línea de negocio:**
```
Folder: Marketplace
Folder: Logistics
Folder: Payments
```

3. **Híbrido (recomendado para DataMartX):**
```
Folder: Production
├── Folder: Marketplace
├── Folder: Logistics
└── Folder: Payments
Folder: Non-Production
├── Folder: Staging
└── Folder: Development
```

**Best practices:**
- Máximo 7 niveles de profundidad (aunque recomienda ≤4)
- IAM policies en folders aplican a todos los proyectos hijos
- Usa folders para aplicar organization policies específicas
- Etiqueta folders para reporting de costos

**Error común:** Crear folders por "tipo de recurso" (ej: Folder: Compute, Folder: Storage). Esto no escala y rompe la herencia de IAM.

### Projects: La Unidad Fundamental

Todo recurso en GCP pertenece a un proyecto. Es la unidad de:
- **Billing** (puede tener su propia factura o compartir)
- **IAM** (roles y permisos)
- **APIs** (servicios habilitados)
- **Quotas** (límites de uso)

**Diseño de proyectos para DataMartX:**

```yaml
# Patrón recomendado: Un proyecto por aplicación/ambiente
marketplace-prod-us:
  purpose: "Marketplace API - US region"
  billing: shared-with-marketplace-folder
  apis: [compute, cloudsql, gcs]
  
marketplace-prod-eu:
  purpose: "Marketplace API - EU region (GDPR)"
  billing: shared-with-marketplace-folder
  apis: [compute, cloudsql, gcs]
  
payments-prod:
  purpose: "Payment processing (PCI scope)"
  billing: isolated
  apis: [compute, cloudsql, kms]
  labels:
    pci-scope: "true"
```

**Decisiones críticas:**

1. **¿Cuántos proyectos?**
   - **Few projects pattern:** 1 proyecto por ambiente (simple, pero limita escalabilidad)
   - **Many projects pattern:** 1 proyecto por aplicación/region/ambiente (escalable, pero complejo)
   - **Recomendación para DataMartX:** Many projects por aislamiento de compliance y costos

2. **¿Proyectos compartidos o dedicados?**
   - **Compartidos:** Menos overhead, pero riesgo de "noisy neighbor"
   - **Dedicados:** Mejor aislamiento, pero más proyectos que gestionar
   - **Recomendación:** Dedicados para producción, compartidos para desarrollo

3. **Project labels:**
   - Obligatorio para tracking de costos
   - Mínimo: `environment`, `team`, `cost-center`, `application`
   - Usa para chargeback/showback

**Error común:** Crear un proyecto "sandbox" donde todos deployan lo que quieren. Esto es un infierno de seguridad y costos.

### Billing Accounts y Cost Management

La estructura de billing debe alinearse con la jerarquía de recursos:

```
Billing Account: DataMartX Master
├── Subaccount: Marketplace (folder-level)
├── Subaccount: Logistics (folder-level)
├── Subaccount: Payments (folder-level)
└── Subaccount: Corporate (folder-level)
```

**Estrategias de optimización:**

1. **Committed Use Discounts (CUDs):**
   - 1-3 años de compromiso
   - Hasta 57% de descuento
   - Aplica a nivel de billing account

2. **Sustained Use Discounts:**
   - Automáticos por uso sostenido
   - Hasta 30% de descuento
   - No requiere compromiso

3. **Preemptible/Spot VMs:**
   - Hasta 91% de descuento
   - Para workloads fault-tolerant
   - Batch processing, data processing

**Error común:** No etiquetar recursos. Sin labels, es imposible hacer chargeback o identificar waste.

## Mentalidad de Cloud Architect

Un Cloud Architect no piensa en "cómo configurar un proyecto". Piensa en:

1. **"¿Cómo escalará esto en 3 años?"**
   - Si hoy tienes 10 proyectos, ¿puedes manejar 100?
   - ¿Tu estructura soporta adquisiciones/fusiones?
   - ¿Puedes agregar nuevas regiones sin reestructurar?

2. **"¿Quién necesita acceso a qué?"**
   - Principio de mínimo privilegio
   - Separación de duties (dev vs ops vs security)
   - Auditoría de accesos

3. **"¿Cómo controlo costos sin bloquear innovación?"**
   - Presupuestos por equipo, no globales
   - Alertas antes de límites duros
   - Self-service con gobernanza

4. **"¿Qué pasa si hay un breach?"**
   - Aislamiento de blast radius
   - Proyectos PCI separados
   - Logging centralizado

5. **"¿Cómo demuestro compliance?"**
   - Labels para auditoría
   - Organization policies para enforcement
   - Audit logs en proyecto separado

## Errores Comunes en Producción

### 1. No usar Organization Policies
**Error:** Dejar todo abierto y confiar en que los equipos "se portarán bien"
**Solución:** Organization policies para:
- `constraints/compute.restrictProtocolForwardingCreationForExternal`
- `constraints/iam.disableServiceAccountKeyCreation`
- `constraints/storage.uniformBucketLevelAccess`

### 2. Proyectos sin labels
**Error:** Crear proyectos sin etiquetar → imposible hacer chargeback
**Solución:** Organization policy que requiera labels:
```json
{
  "constraint": "constraints/iam.allowedPolicyMemberDomains",
  "listPolicy": {
    "allValues": "DENY",
    "allowedValues": ["requiredLabels:environment,team"]
  }
}
```

### 3. Super Admin con cuenta personal
**Error:** Usar `admin@company.com` como Super Admin
**Solución:** Grupo `gcp-super-admins@company.com` con 2+ miembros

### 4. Un proyecto para todo
**Error:** `datamartx-prod` con 50 servicios y 20 equipos
**Solución:** Separar por aplicación/ambiente/región

### 5. No planear para multi-cloud
**Error:** Diseñar estructura asumiendo que solo usarás GCP
**Solución:** Abstracciones que funcionen en AWS/Azure también (Terraform modules)

## Ejemplos Prácticos

### Ejemplo 1: Crear estructura básica con gcloud

```bash
# 1. Identificar Organization ID
gcloud organizations list
# OUTPUT: datamartx.com (ID: 123456789)

# 2. Crear folders por ambiente
gcloud resource-manager folders create \
  --display-name="Production" \
  --organization=123456789

gcloud resource-manager folders create \
  --display-name="Staging" \
  --organization=123456789

gcloud resource-manager folders create \
  --display-name="Development" \
  --organization=123456789

# 3. Crear proyectos
gcloud projects create marketplace-prod-us \
  --name="Marketplace Production US" \
  --folder=FOLDER_ID_PRODUCTION \
  --labels=environment=production,team=marketplace,region=us

# 4. Habilitar APIs
gcloud services enable compute.googleapis.com \
  --project=marketplace-prod-us

gcloud services enable sqladmin.googleapis.com \
  --project=marketplace-prod-us
```

### Ejemplo 2: Organization Policies con Terraform

```hcl
# main.tf
resource "google_organization_policy" "restrict_regions" {
  org_id = var.organization_id
  constraint = "constraints/gcp.resourceLocations"

  list_policy {
    allow {
      values = [
        "in:us-locations",
        "in:eu-locations"
      ]
    }
  }
}

resource "google_organization_policy" "require_labels" {
  org_id = var.organization_id
  constraint = "constraints/iam.tagKeys"

  list_policy {
    allow {
      values = ["tagKeys/123456789"]  # environment label
    }
  }
}

resource "google_organization_policy" "disable_sa_key_creation" {
  org_id = var.organization_id
  constraint = "constraints/iam.disableServiceAccountKeyCreation"

  boolean_policy {
    enforced = true
  }
}
```

### Ejemplo 3: Estructura completa con Terraform

```hcl
# folders.tf
variable "organization_id" {
  description = "GCP Organization ID"
  type        = string
}

resource "google_folder" "production" {
  display_name = "Production"
  parent       = "organizations/${var.organization_id}"
}

resource "google_folder" "staging" {
  display_name = "Staging"
  parent       = "organizations/${var.organization_id}"
}

resource "google_folder" "development" {
  display_name = "Development"
  parent       = "organizations/${var.organization_id}"
}

# projects.tf
resource "google_project" "marketplace_prod_us" {
  name            = "Marketplace Production US"
  project_id      = "marketplace-prod-us"
  folder_id       = google_folder.production.name
  billing_account = var.billing_account_id

  labels = {
    environment = "production"
    team        = "marketplace"
    region      = "us"
    cost-center = "cc-1001"
  }
}

resource "google_project_service" "marketplace_apis" {
  for_each = toset([
    "compute.googleapis.com",
    "sqladmin.googleapis.com",
    "storage.googleapis.com",
    "bigquery.googleapis.com"
  ])

  project = google_project.marketplace_prod_us.project_id
  service = each.value

  disable_on_destroy = false
}

# iam.tf
resource "google_project_iam_member" "marketplace_devs" {
  project = google_project.marketplace_prod_us.project_id
  role    = "roles/viewer"
  member  = "group:marketplace-devs@datamartx.com"
}

resource "google_project_iam_member" "marketplace_ops" {
  project = google_project.marketplace_prod_us.project_id
  role    = "roles/editor"
  member  = "group:marketplace-ops@datamartx.com"
}
```

## Comparación de Servicios

| Concepto | GCP | AWS | Azure |
|----------|-----|-----|-------|
| Root container | Organization | AWS Account (no hierarchy) | Azure AD Tenant |
| Logical grouping | Folders | AWS Organizations OUs | Management Groups |
| Resource container | Project | AWS Account | Resource Group |
| Policy enforcement | Organization Policies | SCPs (Service Control Policies) | Azure Policy |
| Billing unit | Billing Account | Consolidated Billing | EA/MCA |

## Cost Considerations

**Costos de la estructura de organización:**
- **Organization:** Gratis
- **Folders:** Gratis (hasta 5 niveles sin aprobación)
- **Projects:** Gratis, pero cada proyecto puede tener costos de APIs

**Optimización:**
- Consolidar proyectos similares para reducir overhead de gestión
- Usar folders para aplicar budgets y alerts
- Etiquetar todo para chargeback

**Ejemplo de presupuesto:**
```
Budget: Marketplace Production
├── Alert 1: 50% ($50K/month)
├── Alert 2: 80% ($80K/month)
└── Alert 3: 100% ($100K/month) → hard stop
```

## Examen Tip

**Pregunta tipo certificación:**

DataMartX necesita asegurar que todos los recursos en la organización se creen únicamente en regiones de EE.UU. y la UE. ¿Qué debes configurar?

A) Project labels en todos los proyectos
B) Organization policy con constraint `gcp.resourceLocations`
C) IAM policy en la Organization
D) VPC Service Controls perimeter

**Respuesta correcta:** B

**Explicación:** Organization policies son el mecanismo para aplicar restricciones globales a toda la organización. Project labels son para tracking, no enforcement. IAM policies controlan acceso, no ubicaciones. VPC Service Controls son para data exfiltration, no location restrictions.

## Resumen

- **Organization** es la raíz de todo. Solo hay una por empresa.
- **Folders** agrupan proyectos para gobernanza y billing.
- **Projects** son la unidad fundamental de recursos, billing y IAM.
- **Estructura recomendada:** Folders por ambiente + línea de negocio.
- **Labels** son obligatorios para cost management.
- **Organization policies** aplican restricciones globales.
- **Piensa en escalabilidad:** ¿Tu estructura soporta 10x crecimiento?

**Key takeaways:**
1. Diseña la jerarquía antes de crear recursos
2. Usa folders para gobernanza, no solo organización
3. Etiquetar todo desde el día 1
4. Separar proyectos por compliance requirements
5. Organization policies > IAM policies para restricciones globales

# Day 001 Exercises

## Ejercicio 1: Diseño Arquitectónico

### Ticket ORG-001: Diseño de estructura de organización para DataMartX

**Solicitante:** CTO de DataMartX  
**Prioridad:** Crítica  
**Sprint:** Foundation Setup  

**Contexto:**
DataMartX está iniciando su migración a GCP. El CTO necesita que diseñes la estructura completa de organización que soporte los siguientes requisitos:

**Requisitos de negocio:**
- 5 líneas de negocio: Marketplace, Logistics, Payments, Analytics, Corporate
- 3 ambientes: Production, Staging, Development
- 15 países con operaciones (requiere multi-region)
- Presupuesto anual: $2M distribuidos por línea de negocio

**Requisitos de compliance:**
- Payments debe cumplir PCI DSS (aislamiento estricto)
- Operaciones en Europa deben cumplir GDPR (datos en EU)
- Audit logs centralizados para todos los ambientes
- Separación de duties entre devs, ops y security

**Requisitos técnicos:**
- Cada línea de negocio debe tener autonomía para deployar
- Costos visibles por línea de negocio (chargeback)
- Capacidad de aplicar políticas específicas por ambiente
- Soporte para hasta 200 proyectos en 3 años

**Entregables:**
1. Diagrama de la estructura de organización (Organization → Folders → Projects)
2. Justificación de las decisiones de diseño
3. Estrategia de naming para proyectos
4. Plan de labels obligatorio
5. Estrategia de billing accounts
6. Lista de organization policies críticas

**Criterios de evaluación:**
- Escalabilidad (¿soporta 10x crecimiento?)
- Seguridad (¿aislamiento adecuado para PCI?)
- Cost management (¿chargeback posible?)
- Gobernanza (¿autonomía con control?)
- Simplicidad (¿manejable por equipo de 5 personas?)

## Ejercicio 2: Implementación Terraform

### Ticket ORG-002: Implementar estructura de folders y proyectos con Terraform

**Solicitante:** Platform Engineering Lead  
**Prioridad:** Alta  
**Sprint:** Foundation Setup  

**Contexto:**
El equipo de Platform Engineering necesita que implementes la estructura base de GCP usando Terraform. Debes crear los módulos reutilizables que permitirán a los equipos self-service.

**Requisitos técnicos:**

1. **Módulo de folders:**
   - Crear folders para Production, Staging, Development
   - Soportar nested folders (ej: Production/Marketplace)
   - Variables para organization_id y parent folder

2. **Módulo de proyectos:**
   - Crear proyectos con labels obligatorios
   - Habilitar APIs específicas por tipo de proyecto
   - Configurar billing account
   - Asignar a folder correcto

3. **Módulo de IAM:**
   - Asignar roles a grupos de Google Workspace
   - Soportar diferentes patrones (viewer, editor, admin)
   - Variables para project_id y group emails

4. **Root module:**
   - Orquestar creación de estructura completa
   - Variables para organization_id, billing_account_id
   - Outputs con project_ids y folder_ids

**Estructura esperada:**
```
terraform/
├── modules/
│   ├── folder/
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   └── outputs.tf
│   ├── project/
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   └── outputs.tf
│   └── iam/
│       ├── main.tf
│       ├── variables.tf
│       └── outputs.tf
├── environments/
│   ├── production/
│   │   └── main.tf
│   ├── staging/
│   │   └── main.tf
│   └── development/
│       └── main.tf
├── main.tf
├── variables.tf
├── outputs.tf
└── terraform.tfvars.example
```

**Requisitos de calidad:**
- Código debe pasar `terraform validate`
- Variables con validación (ej: labels no vacíos)
- Outputs con descripciones
- README.md con instrucciones de uso
- Ejemplo de cómo crear un nuevo proyecto

**Entregables:**
1. Código Terraform completo en `solutions/day001/terraform/`
2. README.md con instrucciones de uso
3. Ejemplo de ejecución (comandos terraform)
4. Diagrama de la estructura creada

**Criterios de evaluación:**
- Modularidad (¿reutilizable?)
- Best practices (¿variables, outputs, state?)
- Documentación (¿claro para otros ingenieros?)
- Seguridad (¿no hay secrets en código?)
- Escalabilidad (¿soporta agregar más proyectos fácilmente?)

## Ejercicio 3: Implementación gcloud/Console

### Ticket ORG-003: Configurar organization policies y budgets

**Solicitante:** Security & Compliance Lead  
**Prioridad:** Alta  
**Sprint:** Foundation Setup  

**Contexto:**
El Security Lead necesita que configures las organization policies críticas y los budgets para control de costos. Esto debe hacerse ANTES de que los equipos empiecen a crear recursos.

**Requisitos de organization policies:**

1. **Restricción de regiones:**
   - Solo permitir recursos en us-central1, us-east1, europe-west1
   - Aplicar a toda la organización

2. **Labels obligatorios:**
   - Requerir labels: environment, team, cost-center
   - Rechazar creación de recursos sin estos labels

3. **Service accounts:**
   - Deshabilitar creación de service account keys
   - Forzar uso de Workload Identity

4. **Storage:**
   - Forzar uniform bucket-level access
   - Deshabilitar public access por defecto

5. **Compute:**
   - Deshabilitar serial port access
   - Restringir shared VPC creation

**Requisitos de budgets:**

1. **Budget por folder:**
   - Production: $100K/month
   - Staging: $20K/month
   - Development: $10K/month

2. **Alertas:**
   - 50%: email a team-lead
   - 80%: email a director + slack
   - 100%: email a VP + hard stop (si es posible)

3. **Budget por proyecto crítico:**
   - payments-prod: $30K/month (PCI scope)
   - Alertas más agresivas (40%, 70%, 90%)

**Pasos esperados:**

```bash
# 1. Organization policies
gcloud resource-manager org-policies set-policy ...

# 2. Budgets
gcloud billing budgets create ...

# 3. Verificación
gcloud resource-manager org-policies list ...
gcloud billing budgets list ...
```

**Entregables:**
1. Script de shell con todos los comandos
2. JSON/YAML de las policies creadas
3. Screenshots de budgets en Console (opcional)
4. Documentación de cómo modificar policies

**Criterios de evaluación:**
- Completitud (¿todas las policies requeridas?)
- Correctitud (¿constraints correctos?)
- Automatización (¿script ejecutable?)
- Documentación (¿claro para operar?)
- Testing (¿cómo verificar que funciona?)

## Criterios de Evaluación General

### Ejercicio 1 (Diseño): 40% del total
- **Arquitectura (15%):** Jerarquía lógica y escalable
- **Seguridad (10%):** Aislamiento para PCI, separación de duties
- **Costos (10%):** Chargeback posible, budgets alineados
- **Gobernanza (5%):** Autonomía con control

### Ejercicio 2 (Terraform): 40% del total
- **Modularidad (15%):** Código reutilizable
- **Best practices (10%):** Variables, outputs, state management
- **Documentación (10%):** README claro, ejemplos
- **Calidad (5%):** terraform validate pasa, no hay hardcodes

### Ejercicio 3 (gcloud): 20% del total
- **Completitud (10%):** Todas las policies y budgets
- **Correctitud (5%):** Constraints y configuraciones correctas
- **Automatización (5%):** Scripts ejecutables, reproducibles

### Puntuación total: /10
- 9-10: Staff Engineer level. Arquitectura sólida, código production-ready.
- 7-8: Senior Engineer level. Buen diseño, algunos detalles por pulir.
- 5-6: Mid Engineer level. Funcional pero falta profundidad.
- 3-4: Junior Engineer level. Errores conceptuales importantes.
- 1-2: Necesita repasar fundamentos.

## Tips del Mentor

1. **No empieces escribiendo código.** Primero dibuja la arquitectura en papel.
2. **Piensa en el día 300, no en el día 1.** ¿Tu estructura escala?
3. **Labels no son opcionales.** Sin ellos, perderás el control de costos.
4. **PCI DSS es serio.** Payments debe estar aislado, no solo "lógicamente".
5. **Terraform state es crítico.** ¿Dónde lo guardarás? ¿Quién tiene acceso?
6. **Prueba en staging primero.** Nunca apliques organization policies directo en producción.

¡Buena suerte! Recuerda: un Cloud Architect no resuelve problemas, **diseña sistemas que previenen problemas**.
